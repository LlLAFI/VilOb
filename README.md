# Village Observer V0.34B — Settlement Entity V1

**Release:** 2026-10-09  
**Base:** V0.34A · Structural Audit & Baseline  
**Scope:** Independent Settlement registry, 1:1 tile migration, lifecycle and ownership synchronization. **Not** multi-tile settlement merging.

## 구현

1. `World.v34b = {schema, schemaVersion, revision, nextSettlementSeq, settlements[]}` 신설.
2. 각 ACTIVE Settlement에 `id=st-NNNNNNN`, `nationId`, `coreTileId`, `tileIds:[tileId]`, `lifecycle`, `createdCalendarDay` 저장. `Tile.settlementId`는 역방향 참조.
3. 34A/HF2의 완전 복원 완료 후, 기존 영유 타일을 **타일 ID 오름차순**으로 이관한다. 1:1 대응이며 국가·타일·Person 물리 자산을 옮기지 않는다.
4. 타일 영유권 setter 관찰을 통해 개척/멸망/재영유/영토 양도를 감지한다. 영유국 A→B 직접 전환은 Settlement ID를 **보존**하고, 소유→무소유는 해당 ID를 ABANDONED로 남기며 재영유 시 **새 ID**를 발급한다. 단일 타일 정착지 정책에만 적용한다.
5. 저장 시 `V0.34B`, `v34b` 및 타일의 `settlementId`를 직렬화한다. 로드 시 기존 34A 체인을 통과한 다음 기록 및 역방향 참조를 감사한다. 불일치한 34B 세이브는 **오류를 보고하며 로드를 거부**한다. 원본 저장 파일 자체를 수정하지 않는다.
6. 내장 읽기 전용 검사: `VSim.V034B.inspect(world)`. 정상인 경우 `{ok:true, errors:[]}` 반환. `VSim.V034B.settlementForTile(world,tileId)`로 해당 타일의 Settlement 조회.
7. 34A 로더 계열에서 관측된 **저장된 `birthOrdinal24` 재생성 문제**를 이관 시 원본 저장값 복원으로 보완. 이미 있는 유효한 출생일 값만 복원하며 출산·성장 수식은 변경하지 않는다. 이 수정으로 기존 34A 로더의 무작위 재구성 동작과 비교하면 이후 생애 이벤트가 달라질 수 있다.

## 불변조건

- 영유 타일 **정확히 하나** ↔ ACTIVE Settlement 정확히 하나.
- 무주지/수역 `settlementId=null`.
- ACTIVE Settlement 소유국 `nationId === Tile.ownerId`; `tileIds=[coreTileId]`.
- ABANDONED 기록은 `tileIds=[]`이므로 물리 타일에 더 이상 연결되지 않음.
- `nextSettlementSeq > max(existing settlement ID sequence)`.
- `Tile.ownerId`는 여전히 영유권만 표현한다. `v33OccupierId`는 별도 일시 점령.
- Person `homeTileId`, `workTileId`, `villageId`, 시설, 재고, 경제, 전쟁 및 AI 의사결정 경로 자체는 유지.

## 대용량 사용자 저장 파일

사용자의 **67년 1분기 15일 / Person 854 / 영유 타일 276 / 96.80MB** 원본 파일은 전달받지 못했으며 아직 34B 로더에서 실제로 불러오지 않았다. 해당 상태를 **34B에서도 읽어 검증했다고 주장하지 않는다.**

1. 34A 원본 세이브는 별도로 보관한다(덮어쓰지 않음).
2. **34B `index.html`에서 기존 세이브 가져오기** → 날짜 진행 전에 새 34B 파일로 내보내기.
3. **34B `save-validator.html`**로 새 파일을 검사해 경량 `v034B-audit-...json` 보고서 다운로드.
4. **34B 검사기의 보고서 비교 UI**에서 이미 받은 34A 보고서(`v034A-audit-67y-...json`)와 이번 보고서를 비교한다.
5. 기대: ACTIVE 276, ABANDONED 0, Nation/Tile/Person 지문 불일치 0건, 구조 오류 0건. 한 항목이라도 다르면 실행을 계속하지 말고 원본을 유지해 원인 파악.
6. 세이브 96.80MB의 약 87%를 차지하는 Telemetry는 이번 패치에서 절대 삭제·압축하지 않는다. localStorage 용량 한계를 넘으면 **파일 다운로드** 방식을 이용한다.

```javascript
const world = window.villageObserver.world;

console.table(report.errors);
```

오류가 발생한 경우 각 진단 항목에는 code, tileId, nationId, personId 등의 식별자가 포함된다. 이 함수는 읽기 전용으로 설계했으며 자동으로 매일 실행되지 않는다. 과거 버전의 실제 장비 회계는 `VSim.V033I1.audit`도 확인한다.

# Village Observer — V0.33I3C 상세 README

## 1. 왜 I3C가 필요한가

I3B에서는 OPENING의 검/창/도끼 근접 공격력 기여를 0으로 만들었지만, 모든 사상자가 라운드 마지막에 일괄 발생했다. 따라서 실제 궁병이 개전 사격으로 상대를 저지하거나 다음 단계의 적 병력을 줄이지 못했다. I3C에서는 기존 진짜 D 전쟁 엔진 내부의 Person 전사·부상 처리를 순차적으로 호출한다. 단순한 가산 전투력 보너스가 아니다.

## 2. I3C의 물리·확률 전투 모델

### 첫 라운드 단계

1. 원거리 무기가 양측 중 하나에 존재: `OPENING 35% → CONTACT 20% → MELEE 45%`.
2. 양측 모두 원거리 무기가 없음: `CONTACT 4/13(약 30.77%) → MELEE 9/13(약 69.23%)`. OPENING은 아예 건너뛴다.
3. 두 번째 라운드 이후: `MELEE 100%`.

**단계 가중치는 라운드 시작 시 확정한다.** 한 단계에서 궁병이 전멸하더라도 남은 동일 라운드의 CONTACT/MELEE 가중치를 갑자기 바꾸지 않는다. 대신 실제 남아 있는 병력·무기·방어구·Screen이 재계산된다.

### 첫 라운드 OPENING에서 누가 누구를 공격하는가

`OPENING = 1.10 × 개인 무기의 ranged 값`이다. ranged 값이 없는 검·창·도끼는 0. 고유 Person 장비, 훈련·보급·사기·지휘관, 지형을 사용한 공격 단계 전투력을 실제로 평가한다. **한쪽 OPENING 전투력이 0이면 그쪽이 상대에게 가하는 OPENING 사상자는 무조건 0**이다. 원거리 무기끼리라면 양측 사격이 모두 가능하다.

### 피해 정산 순서

1. 해당 단계 진입 직전 양측의 **실제 살아 있는 활성 Person**, 장착 무기·방어구, 전열 수 및 Screen, 평균 관통과 유효 방호력을 재계산한다.
2. 단계 전투력의 상대 비율로 기존 0.33D의 승리측/패배측 사상률 함수(`winnerRate`, `loserRate`)를 사용하되 해당 단계 **가중치를 곱해** 피해를 배분한다. 공격 전투력이 0인 쪽의 가해율은 0이다.
3. **양측 사상자 대상 명단은 같은 단계 시작 시점에서 먼저 모두 추첨**한다. 한쪽을 먼저 제거해 반대편의 같은 단계 사격 기회를 빼앗지 않는다.
4. 그다음 실제 Person 전사/부상에 반영한다. 부상자는 현 라운드 이후 전투에서 빠지고, 전사자는 기존 I1A2·I1A1 장비 캡처·전장 회수·유실 lifecycle을 따른다.
5. 다음 단계에서 갱신된 전투 병력과 Screen으로 다시 전투력을 계산한다.

**사상자 예산 상한:** 한 라운드에서 각 진영이 잃는 인원은 라운드 시작 인원 × 30%의 올림 값 이하이다. 6명 편제는 단계 합계 최대 2명. 이 상한은 순차 판정이 기존 라운드 정산보다 중복 사상자를 급증시키는 현상을 막기 위한 I3C V1 안전장치이며, 향후 대규모 전쟁 자료에 따라 재검토 가능하다.

**전사 확률·방어구:** I2의 유효 방호력, 사상 노출(1−0.75×유효 방호력), 전사 분기확률(0.36×(1−0.35×유효 방호력))은 유지한다. 전사/부상은 확률적이므로 OPENING 공격이 가능한 라운드에서 항상 사상자가 나와야 하는 것은 아니다.

**최종 라운드 판정:** 실제 해당 단계에서 평가된 가중 전투력을 합산해 기존의 라운드 승패 및 3연패 전열 붕괴(수도 일부 예외)를 판정한다. **사상자 발생 여부는 전투 승리의 필수 조건이 아니다.**

# Village Observer — V0.33I3B

**패치명:** Ranged-Only Opening + Conditional Contact V1  
**기준선:** V0.33I3A (Combat Scenario Isolation & Validation)  
**버전:** 0.33I3B · 2026-10-08

## 1. 패치 목적 및 범위

V0.33I3A A1(기초 창 vs 철제 검) 및 A2(철제 창 vs 철제 검) 실험을 **완료·종료(CLOSED)** 처리한다. A1/A2는 이번 배포의 실험 파일에서 제거하지만 이전 세이브 호환성은 유지한다. 이번 활성 실험은 **B(Screen), C(Protection/Penetration), D(Opening vs Melee)** 세 가지다.

가장 큰 논리 수정은 OPENING을 '전열 충돌 이전의 원거리 개전'으로 재정의한 것이다. 구버전 I2는 근접 전용 무기도 OPENING에서 `0.55 × melee` 공격력을 제공했으나, I3B에서는 이를 0으로 바꾼다. 변경은 실험실뿐만 아니라 **일반 자연전쟁의 정식 D Engagement**에도 적용된다.

### 1.1 개전 및 접촉 공식

개인 무기의 통계는 I1/I2 레지스트리 데이터를 그대로 읽는다. 무기의 새로운 스탯 값을 도입하지 않는다.

```
OPENING = 1.10 × ranged
CONTACT = 0.45 × melee + 0.75 × reach
MELEE   = melee + ranged × rangedSustain × Screen
Screen  = clamp(2 × 근접전 가능 인원 / 전체 참여 인원, 0, 1)
```

- `ranged=0`인 검·창·도끼는 OPENING에서 공격력 0이다.
- 활·투창 등 `ranged > 0`인 무기는 OPENING 공격에 기여한다.
- 투창(HYBRID)은 근접전 가능 인원에도 포함된다.
- 타일 사이 원거리 사격이나 장거리 이동·탄약 체계는 도입하지 않는다.
- 단계별 전투력 기여를 합산한 뒤 **라운드 종료 시점에 기존 I2 사상자 판정을 단 한 번** 실행한다. 따라서 아직 OPENING 중 사상자가 CONTACT 전에 전열에서 빠지는 순차적 단계 모델은 아니다.

### 1.2 1라운드 가중치의 조건 분기

| 교전 상태 | OPENING | CONTACT | MELEE | 의미 |
|---|---:|---:|---:|---|
| 양측 어느 한쪽이라도 원거리 공격 무기 보유 | 35% | 20% | 45% | 원거리 개전 포함 |
| 양측 모두 원거리 공격 무기 0 | **0%** | **30.7692%** | **69.2308%** | 사용하지 않는 원거리 구간을 두 근접 단계에 재배분 |
| 2라운드 이후 | 0% | 0% | 100% | 지속 난전 |

원거리 소유 판정은 실제 전장 양측의 살아 있는 활성 Person 장비에서 `ranged > 0`을 확인해 정하며, 국가 프로필·미래 장비 계획은 영향을 주지 않는다. 원거리 공격수가 전사하거나 부상해 두 번째 라운드에 사라지더라도 기존 '2라운드 이후 MELEE 전용' 규칙은 유지한다.

### 1.3 질적 전투력 정규화

총 전투력 공식을 기존 I2의 Person 기반 훈련·보급·사기·지휘·방호력 구조 그대로 유지하며, '기초 창의 같은 시나리오 내 기준 전투력 = 1'이 되도록 분기별 기준점만 변경한다.

```
RANGED_PRESENT_FIRST reference = 0.616800
NO_RANGED_FIRST      reference = 0.9489230769
LATER_MELEE          reference = 0.920000

quality = (w_open × opening + w_contact × contact + w_melee × melee) / reference
```

이를 통해 무기 구성을 바꾼 병력이 전투 화면에서 의도치 않게 중복 장비 보정을 받지 않도록 한다. 나머지 I2 처치율·`effectiveProtection=clamp(armor-0.65*penetration,0,0.45)`·전사 확률 계산은 변경하지 않았다. 양측 난수 0.92~1.08, D Engagement의 3~5일 주기 및 기존 퇴각·사기·장비 회수 시스템도 유지한다.

## V0.33I3A 이전 기술 문서 (호환성과 변경 전 기준선 보존)

# V0.33I3A — Combat Scenario Isolation & Validation

**기준선:** `V0.33I3` · **패치 날짜:** 2026-10-08 · **패치 유형:** 전투 실험 시나리오 안정화. I2 전투/장비 밸런스 수치를 수정하지 않음.

## 1. 목적 및 회귀 버그

이전 I3-A 실전 시나리오에서 '창병 6 vs 검병 6'이라 표시했지만 실제 첫 `BATTLE33`은 **키오 10명(창 6명 + 수도 주둔군 4명) vs 델마 6명**이었다. 다음 라운드에서는 일반 Formation AI가 델마 병력을 HOME으로 돌려 9 vs 3이 되었다. 충분한 식량도 없어서 모든 국가가 Recovery에 들어갔고, 출생과 비전투 아사 등이 실험을 오염시켰다.

I3A는 **실제 Person-backed V0.33D Engagement와 I2 무기/방어구 계산을 보존**하면서, Test Scenario로 명시한 실험 세계에서만 일일 경제·인구·국가 의사결정·동원·행군을 우회한다. 일반 자연 세계는 기존의 World.advanceOneDay 체인을 그대로 실행한다.

## 2. Native Combat Isolation V1 구현

1. 식별자 `testScenario.category='combat-regression'`, `testScenario.id='I3A-…'`, `world.v33i3a.mode='ISOLATED_NATIVE_COMBAT'` 세 조건이 모두 맞는 세계에만 격리 루프가 적용된다. 일반/이전 I3·I2 데이터는 격리하지 않는다.
2. 실험 전장으로 **기존 소유권이 없는 통행 가능한 일반 육상 타일**을 선택한다. 수도에 딸린 CORE_GARRISON은 참전하지 않는다.
3. 국가 0(A: 키오), 국가 1(B: 델마) 각각 **실제 Person 정확히 6명**만 Formation에서 선택·배치한다. 실제 Cohort, Formation, Person ID, weaponId/armorId를 보존한다.
4. AI의 목표 변경으로 편제가 바뀌지 않도록 격리 세계에서 `ensureFormationsD`의 일반 재편성 경로만 우회하여 현재 물리 편제를 그대로 조회한다. 인위적인 병력, 숨은 지원군을 생성하지 않는다.
5. **첫 라운드 직전** Engagement를 생성한다. 원래 `startEngagementD()`의 자동 첫 라운드는 I3A 실험에 한해 지연된다. 이외의 게임에서는 기존 즉시 첫 라운드가 그대로 적용된다.
6. '하루 진행'은 V24 360일 역법의 calendar day 1개만 움직이며 일반 Person daily tick, 연간 경제, 연구, 출산, 아사, 건물 유지보수, 병력 이동, War Intent/Peace AI 등을 실행하지 않는다. 대신 기존 `V033D.engagementRound()`만 정해진 3~5일 간격으로 호출한다.
7. I1A2 전사 장비 유실/회수, 개인별 실제 부상·사망, 전투 사기, 훈련·지휘관 계산, I2 Screen/관통·방호와 타일별 I3 기록관은 유지한다.
8. 승부가 결정되어 Engagement가 끝나면 시나리오는 `DONE`으로 표시된다. 추가 일일 진행 시 새 전투를 생성하지 않는다.

### 통제조건 검증

`VSim.V033I3A.validate(world)`는 전장 중립성, Engagement 개시 전 0라운드, 첫 라운드 스냅샷 6명/6명, 국가별 실제 Person/무기/방어구/Formation 구성을 검증한다. 실패한 경우 첫 라운드를 자동 진행하지 않고 실험 상태를 `ERROR`로 표시한다. 전사·부상에 따른 인원 감소는 정상적인 결과다.

### 최초 장비 출처

시나리오 초기 배급은 `SCENARIO_STARTING_EQUIPMENT`로 구분하고 국가별 장비 장부의 `migratedByItem`에 각 무기와 갑옷을 1개씩 등록했다. **일반 생산과 무관한 테스트 전용 초기 물자**이며 실물 보존식으로 검산한다. 전사 시에는 기존 I1A2의 회수/공식 유실 수명주기가 실행된다.

- 시작 시나리오 **READY(첫 라운드 직전)** 상태를 독립 원본으로 보관하고 반복마다 복제하여, 동일 Person·장비·Cohort·Formation 조건으로 시작한다.
- 반복마다 난수 시드 `12345 + trialIndex × 2654435761` 기반 독립 난수열을 사용한다. 같은 원본·시드·횟수라면 재현 가능하다.

- **원본 UI의 현재 세계는 변경하지 않는다.** 수십~수백 차례 전투는 CPU를 사용하므로 필요에 따라 적은 반복부터 시험한다.

**중요:** 이전 I3 `I3 전술 통제실험실` 메뉴는 여전히 **I2 단순화 계산기**이며 D 전체 교전은 아니다. 새 `-lab.json` 파일 6개는 빠른 수치 탐색용으로만 사용한다. 정확한 실전 승률은 이번 I3A **Native 반복** 결과를 우선한다.

# Village Observer V0.33I3 — Tactical Battle History & Combat Laboratory

> 패치일 2026-10-08 | 기준 V0.33I2 | 범위: 관측·실험·저장 기능. **I2 전투 밸런스, I1A2 장비 보존 규칙, 전쟁 AI는 유지.**

## 1. 버전 목적

V0.33I2는 실제 Person의 무기·방어구 성능을 합동전쟁의 0.33D Engagement에 반영했다. I3에서는 **각 타일에 발생한 실제 전투(Engagement)를 최근 게임 시간 1년, 360일 동안 기록**하고, 전투를 열면 **라운드별 전열·후열 구성 및 OPENING/CONTACT/MELEE의 단계별 공세 우위**를 보여준다. 동시에 **통제된 무기 비교 실험**을 제공한다.

## 2. 타일 전투 히스토리

- 지도에서 타일을 선택하면 **최근 전투 기록** 목록이 표시된다. 전투는 `Engagement` ID로 구별하며, 매일 독립된 사건으로 중복 생성하지 않는다.
- 각 전투의 시작·종료 날짜, A/B 측, 국가별 색상, 결과 및 라운드 수를 표시한다. **전투 목록의 항목을 클릭**하면 전투 상세가 펼쳐진다.
- 초기 전투 기록은 `startEngagementD`의 유효한 접전 발생 시점에 저장하며, 각 `engagementRoundD`에서 실제 전투 전/후 Person 장비·병력 스냅샷을 취득한다. `finishEngagementD`에서 종료 사유와 승리 측을 확정한다.
- **종료 이후 360 calendar-day** 동안 유지한다. 진행 중인 Engagement는 360일이 넘어도 지우지 않는다. 게임 날짜가 흘러 만료되면 자동 정리하고, 열람·저장 시에도 정리한다. 타일 주인이 바뀌어도 과거 기록은 기존 타일 ID에 유지된다.
- I2 또는 이전 버전의 기존 세이브는 불러올 수 있지만 **과거 전투의 전열·후열을 추정해서 복원하지 않는다**. I3에서 발생한 교전부터 관측한다.
- 저장 위치는 `world.v33i3.byTile[tileId]`; 하나의 전투 내에 여러 `rounds[]`를 포함한다. 버전은 `0.33I3`이며 별도 로컬 저장 키 `village-observer-v0-33i3`를 사용한다.

### 라운드 데이터

- 전투 전/후 각 측 실전 Person 인원 수, 근접 전열과 원거리 후열 인원·무기 종류/갑옷 종류, 참가 국가별 병력 수.
- `Screen`, 평균 Penetration, 유효 Protection, 장비 품질 배율, 실제 라운드 승자, 라운드별 총 전투력, 국가별 사망·부상 집계.
- 첫 라운드 가중치: OPENING **35%** / CONTACT **20%** / MELEE **45%**. 두 번째 이후 라운드: MELEE **100%**.
- 압박 막대는 실제 I2 `roundPower`에서 **각 Person의 기초전투력·지휘 효과·유효 방호력까지 반영해 누적한 단계별 전투력 기여**를 사용한다. 지형 계수는 반영하고, 단계별로 공통 확률변동을 분해할 수 없어 **최종 난수는 반영하지 않는다**. 이는 **실제 전열의 거리 이동을 나타내는 그림이 아니다**.
- 사상자는 각 단계별로 독립 산출하는 것이 아니라 I2의 **해당 라운드 최종 1회 피해 정산 결과**를 표시한다. 단계별 사상 수치를 조작해 만들지 않는다.
- 색상은 전투 발생 시점의 국가 `fillColor`/`borderColor`를 저장한 스냅샷을 사용한다. 합동전쟁의 여러 참가국을 해당 국가별 칩으로 구별한다.

### 사용자 화면 및 갱신

- 타일 Inspector 하단에 목록을 추가. 하나의 전투를 클릭하면 라운드별 접기/펼치기 상세가 나온다.
- 라운드의 좌우 전열/후열 장비 조합은 실제 Person 기반이다. 인원 수가 많아도 무기·국가별 `×N`으로 묶어 화면을 보호한다.
- 상세창 선택 정보와 라운드 열림 상태는 UI 객체에 보존하여 틱 렌더 시 반복 초기화되는 문제를 줄인다.

## 3. 실험 시나리오 — 두 가지 종류

이번 배포물에는 **서로 다른 용도의 JSON**이 들어 있다. 서로 다른 입력 위치를 사용한다.

### A. 실제 전쟁 엔진 시나리오 (4개, `I3-*-native-*.json`)

**사용 방법:** 게임의 기본 **「테스트 시나리오 V1」 → 「시나리오 파일」**에서 해당 JSON을 불러온다. 현재 게임 세계가 해당 시나리오로 전환되므로 중요한 세계는 먼저 저장한다. 타일 기록관에서 첫 전투 라운드를 확인한 뒤 게임을 진행하면 후속 라운드가 축적된다.

이 파일들은 기존의 **`village-observer-test-scenario` v1** 완전한 세계 세이브 래퍼이다. 초기 상태는 실제 Person, 실물 장비, 기존 Cohort, Formation, 선언된 전쟁, 시작된 Engagement를 포함한다. 양측은 6명씩 참여한다. 첫 라운드는 이미 완료되어 있으며 둘째 라운드부터 게임을 진행하면 된다.

| 파일 | 편제 | 의도 |
| --- | --- | --- |
| `I3-A-native-spear-sword.json` | 기초 창 6 vs 철제 검 6 | CONTACT 대비 MELEE 우위 |
| `I3-B-native-screen.json` | 활 4 + 기초 창 2 vs 기초 창 6 | Screen = 0.667인 혼합군 |
| `I3-C-native-armor.json` | 초기 사슬갑 철제 검 6 vs 직물갑 철제 도끼 6 | 관통·방호 상성 |
| `I3-D-native-opening.json` | 활 3 + 철제 검 3 vs 철제 검 6 | 첫 라운드와 지속 난전 비교 |

네 파일의 장비는 **테스트 시나리오 시작 지급품**이다. 국가 재고·장착 보존식을 깨지 않도록 `SCENARIO_STARTING_EQUIPMENT` 출처로 별도 메타데이터에 기록하며, I1 기존 감사식의 초기 재고 원천 장부(`migratedByItem`)에도 입력한다. **실제로 원자재를 생산해 만들어진 물품이라고 주장하지 않는다.** 자연 세계의 군수 제작 규칙과는 별개이다.

실전 시나리오는 기존 D 전쟁 AI·점령·이동·전사·회수 모델을 사용한다. 진행 시간이 길어지면 AI 개입 등 외생 조건이 생길 수 있으므로 **완전한 반복·동일 조건 통제**가 필요하면 아래 Lab을 사용한다.

### B. 반복 통제 실험실 시나리오 (5개, `I3-*-combat-lab.json` 등)

**사용 방법:** 저장/테스트 시나리오 영역 아래에 추가된 **「I3 전술 통제실험실」 → 「실험 시나리오 JSON」**에 해당 파일을 선택한다. 반복 횟수 30/100/300을 선택하고 **「통제실험 실행」**을 누른다. 일반 세계 진행이나 Person 재고를 변경하지 않는다.

파일 형식은 `village-observer-combat-lab` v1이다. I2의 **실제 장비 전투력 계산 함수 `calculateRound()`와 실제 피해자 추첨 함수 `casualties()`**를 재사용하며, 라운드당 기존 D의 기본 승자·패자 피해율을 적용한다. 실험은 고정된 훈련·보급·사기·동일 인원으로 구성되며, 각 비교 조건은 동일 시드(기본 `12345`)에서 실행한다. 실험 A/B 측별 승률, 첫 라운드 승률, 평균 라운드 수, 평균 사상자와 단계별 전투력을 반환한다.

**실험실의 범위 제한:** D 전쟁 AI·보급 경로/지형/지휘관·영토 점령/전쟁 피로 및 E1 소부대 피해 완충 등의 전체 시뮬레이션을 실행하는 것이 아니다. 독립 계산기의 평균 승률을 자연전쟁의 실제 승률이라고 확대 해석하지 않는다. 실제 Engagement의 동작·회수·영속성은 위 네 실전 시나리오로 별도 검증한다.

| 파일 | 조건 수 | 목적 |
| --- | ---: | --- |
| `I3-A-spear-sword.json` | 3 | 기초·철제 창과 검, 혼합군 비교 |
| `I3-B-screen.json` | 4 | 근접 엄호 0/0.333/0.667/1.0 비교 |
| `I3-C-armor-penetration.json` | 4 | 사슬·찰갑·직물 + 도끼/검 비교 |
| `I3-D-opening-melee.json` | 3 | 활·투창·검 혼합 대비 지속 난전 |
| `I3-ALL-combat-lab.json` | 14 | 네 범주 14조건 종합 실행 |

통제실험실 장비 아이템 ID는 실물 I1 Registry를 사용한다. I2 수식·무기 Registry에 임의 버프나 페널티를 추가하지 않는다.

## 4. 버전 호환성과 제외 범위

- 실제 공격력·사상률·I1A2 장비 유실 확률, 자동화 국가 전쟁 AI, 기본 경제·기술·영토 규칙 **변경 없음**.
- I2 계산에 관측용 3단계 원시 전투력 누적을 추가했으나 기본 라운드 총 전투력 공식에는 영향을 주지 않는다. 추가 시뮬레이션 난수 호출 없음.
- I1A2의 사망자 장비 정산·재고 입고·전장 유실·회수 로직은 그대로 이용한다.
- 타일 내부 실제 좌표/병사의 위치 이동·애니메이션·전투 자동 리플레이 재생 없음.
- Person 개별 공격 순서의 날조나 단계별 별도 사망 추첨 없음.
- I3는 관측+시나리오를 주목적으로 하고, 군사 AI의 실제 장비 선택/전열 편제 최적화는 후속 검토 대상이다.

## 5. 검증

- 전체 HTML 내 **127개 JavaScript 스크립트의 구문 검사 통과**.
- Headless Chromium의 직접 HTML 실행에서 I3 버전 표시·UI 패널 정상 초기화, JS 예외 0건.
- 5개 Lab 시나리오(총 14비교 조건), 30회 반복 각 실험 및 동일 시드 재실행 결과 일치 확인. 별도로 Screen 0→1 변화 실험 100회 실행.

## 1. 릴리스 목적

이 릴리스는 I1/I1A/I1A1/I1A2에서 구축한 **실물 장비 생산 → 지역 재고 → 실제 Person에게 지급 → 회수·유실** 흐름을 변경하지 않고, 실제 Person이 장착한 무기/방어구 능력치를 **정식 V0.33D 다국적 합동전투 라운드**에 반영한다. 이전 세션 합의를 기준으로 첫 교전 라운드는 `OPENING 35% + CONTACT 20% + MELEE 45%`, 이후 모든 라운드는 `MELEE 100%`로 진행한다.

합의대로 I2는 군사 AI가 자동으로 전술 대형을 선택하는 기능, 상세 전투 UI 전면 재설계, 신규 대량 장비 및 대규모 전투 밸런스 변경을 포함하지 않는다. 해당 범위는 I3에 남긴다.

## 2. 전투 엔진 적용 위치

- 실제 전쟁의 교전 엔진은 `engagementRoundD()` 및 `applyCoalitionCasualtiesD()`이다. I2는 이 두 함수의 기존 승패·사상·전장 회수 흐름에 전술 판정과 노출·방호 위험도만 삽입한다.
- 이전의 `forcePower33()`/`battle33()`은 호환·구형 경로로 남으며, 현대 다국적 전투는 D 엔진이 소유한다.
- `NS.V033H.intrinsicUnitPower()`에서 실제로 호출되는 H2 내부 함수를 I2 전술 자체 전투력으로 교체한다. 평시 지도에 표시되는 전투력은 **상대 장비·지형·전투 난수 적용 전의 기준 전투력**이다.
- 재편, 전투 후 사기 충격, 후퇴, Engagement 라운드 간격(3~5일), 교전 종료 판정, 점령·평화협정은 기존 규칙을 유지한다.

## 3. 첫 교전과 지속 교전

| 교전 시점 | OPENING | CONTACT | MELEE |
|---|---:|---:|---:|
| 최초 라운드 | 0.35 | 0.20 | 0.45 |
| 2라운드부터 | 0 | 0 | 1.00 |

- 사격은 **실제 적대 병력이 같은 타일에 있을 때** 발생하는 교전 라운드 안에서만 평가된다. 인접 타일 원거리 공격은 없다.
- 등록 무기 능력치는 기존 `NS.V033I1.equipmentRegistry`를 그대로 활용한다.
- 각 Person의 장비로 계산한 단계 공격지수는 `OPENING = 0.55×melee + 1.10×ranged`, `CONTACT = 0.45×melee + 0.75×reach`, `MELEE = melee + ranged×rangedSustain×Screen`이다.
- `reach`는 CONTACT에만 직접 들어간다. `rangedSustain`에 대응하는 활·투창 지원사격은 후속 MELEE에도 남는다.
- `Screen = clamp(2 × 근접 병력 수 / 총병력 수, 0, 1)`로 계산한다. `mode !== RANGED`인 사람은 근접 병력으로 계산하므로 `MELEE`, `HYBRID`, 무장하지 않아 임시 곤봉을 쓰는 Person 모두 Screen 제공자가 될 수 있다. 아군 여러 국가의 병력이 동일 교전 편에 있으면 Screen을 합산한다.
- 같은 Person의 무기·방어구 슬롯은 `militaryEquipment33I1`의 실물 데이터만 읽는다. 무기 미지급자는 `improvised_club`의 기본 근접 능력치로 싸운다. 별도의 가상 물자 생성은 없다.

### 3.1 무기 단계 지수 정규화

기존 등록된 기초 창(`basic_spear`, melee 0.92, reach 0.80)을 새로운 합성 전투력의 기준점으로 설정한다.

- 최초 기준지수 `BASE_FIRST = 0.35×(0.55×0.92) + 0.20×(0.45×0.92+0.75×0.80) + 0.45×0.92 ≈ 0.7939`.
- 후속 기준지수 `BASE_MELEE = 0.92`.
- `전술 배율 = (단계별 총합 지수) / (해당 라운드 기준지수)`.

이 정규화는 새로운 I2의 구현상 기준치이며 이전 대화에서 별도의 숫자로 확정된 밸런스는 아니다. 기초 창을 기준으로 무기 간 상성을 비교하기 위한 기본값으로 사용한다.

### 3.2 Combat Power 변경

기존 추상 `Equipment/250` 항목을 **제거**하고 다음 Person 기준 전투력을 사용한다.

`기본 Person 전투력 = 0.42 + Cohort.training/250 + Cohort.supply/280 + Cohort.morale/400`

`Person 유효 전투력 = 기본 전투력 × 지휘관 계수 × 단계별 전술 배율 × (1 + 0.30 × 유효 방호력)`

이후 합동 편의 Person 전투력을 더하고 기존 소유영토 지형·요새 효과 및 전투 난수 0.92~1.08을 한 번 적용한다. 지휘관은 기존 시스템에서 제공하는 수치를 그대로 사용한다. 개인 능력치를 별도 신규 배율로 중복 가산하지 않는다.

`(1 + 0.30 × 유효 방호력)`는 전투력에서 방어구의 의미를 작게 반영하기 위한 I2 초기값이며, 이후 장기주행으로 검증할 대상이다. 무기·방어구 보급률 기반 추상 보너스를 다시 더하지 않는다.

## 4. 관통/방호/피해

이전 합의의 계산식을 사용한다.

- `P_eff = clamp(P_armor − 0.65 × P_penetration, 0, 0.45)`
- `CasualtyMultiplier = 1 − 0.75 × P_eff`
- `DeathChance = 0.36 × (1 − 0.35 × P_eff)`

적 교전 편의 실제 장착 무기 관통력 평균을 `P_penetration`으로 사용한다. 공격자에 따라 같은 방어구의 방호 효과가 달라진다. 유효 방호력은 개인마다 다르므로, 사상자 수는 `Σ(기존·E1 보정 사상률 × 개인 CasualtyMultiplier)`를 확률적으로 정수화하고, 사상자 대상은 실제 Person의 노출도에 따라 가중치 추첨한다. 추첨 후 해당 Person의 `DeathChance`로 사망 또는 부상을 결정한다. 사상자를 세 전투 단계에서 각각 생성하지 않는다.

**전투 사망 장비 처리:** 기존 `NS.V033I1A1.captureBattleDeath` → 패전/승전 회수 확률 → Formation 회수 캐시 → 자국 supply-node 입고 또는 공식 영구 유실 처리 경로를 그대로 유지한다. 부상자는 장비를 계속 보유한다. 인구 상태와 군사 cohort 정리는 기존 D 엔진을 사용한다.

### 2.2. 확인된 실행 순서 오류

기존 V0.24 일일 인구 루틴 `dailyDemography24`는 `killPerson24`에서 `p.alive=false`로 표시한 후 `v.residents=v.residents.filter(p=>p.alive)`로 주민 배열에서 사망자를 제거한다. 반면 I1A1의 일반 장비 반환 루틴은 `Person.ageOneYear` 래퍼, `Village.dailyTick`의 `reconcile` 또는 이후 군사 감사에 의존한다. 질병·노환이 **일일 인구 처리**에서 발생한 경우, Person 객체가 군사 정산에 도달하기 전에 주민 배열에서 사라진다. 따라서 `equippedCounts`와 재고에서 동시에 해당 장비가 없어져 장부 결손이 발생할 수 있었다.

### 3.1. 비전투 사망 `NONCOMBAT_DEATH`

- `weaponId`와 `armorId`가 물리적으로 반환되면 각각 원 소속 국가의 유효 공급 노드 inventory에 1개 입고되고 Person 슬롯은 `null`이 된다.
- `dailyDemography24`의 주민 필터 직전에는 다른 경로에서 이미 `alive=false`가 된 인물도 보호하도록 `PRE_REMOVAL_DEATH` 보조 검사를 추가한다.
- 슬롯이 이미 `null`이면 반환을 반복하지 않는다. 관측 이벤트도 실제 회수된 경우에만 증가한다.
- 기존에 `starvation25` 사망 뒤 일반 군사 정산에 의해 회수되던 로직은 유지한다. 노환·질병의 인구 확률과 전투 사망률은 변경하지 않는다.

### 3.2. 외부 이주 `EXTERNAL_MIGRATION`

- 기존 기근 이주/국가 간 Person 이동 코드에서 주민을 출발 국가 roster에서 제거하기 전에 원 소속 국가 장비를 회수한다.
- 이주자의 신상, 이름, 문화, 개인 소지 Gold와 기존 이주 동기는 그대로 유지한다.
- 이주 후 수용국은 필요하면 기존 실물 지급 조건에 따라 새 장비를 지급한다. 장비를 국가 사이에 순간이동하거나 새로 생성하지 않는다.

### 3.3. 평화협정 영토 양도 `PEACE_CESSION`

- 영토와 함께 국적이 변경되는 Person에 대해 `demilitarizeTransferred` 및 주민 roster 이동 **직전** 원 소속 국가 장비를 반납한다.
- 이 조치는 **주민이 장착한 장비**의 생애주기만 다룬다. 영토에 남은 군수창고 자체의 소유권/약탈/점령물자 정산 시스템은 이 릴리스에 추가하지 않는다.
- 기존 0.33F 전쟁 종결·영토 연결성·Gold 배상·인구 귀속 규칙은 유지한다.

### 3.4. 이전 I1A1 세이브의 결손 처리

장비가 이미 주민 roster에서 사라진 I1A1 저장에는 원래 장비를 회수할 사람과 위치가 남지 않는다. 그러므로 이전 결손을 소급해 재고에 더하지 않는다.

- **명시적으로 V0.33I1A1 버전 세이브를 Import/Load**하는 경우에만 각 국가/품목의 설명되지 않는 **양(+) 결손**을 1회 계산한다.
- `legacyUntrackedByItem`에 넣어 기존 회계식의 구분된 항목으로 보존하고, 새 `preI1A2UntrackedLoss`에 그 수량을 별도 표시한다.
- `MILITARY_EQUIPMENT_PRE_I1A2_DEFICIT_CARRIED` 이벤트에 국가·품목·수량·소스버전을 기록한다.
- 이미 보존 항목으로 정리된 과거 손실은 새 세이브 로드에서 다시 더하지 않는다.
- 새 세계와 신버전 저장에는 이전 결손 이전 처리를 적용하지 않는다.
- 음(-)의 결손, 즉 설명되지 않는 잉여는 자동 정리하지 않고 계속 보존 오류로 보고한다.

**주의:** 이전 데이터의 `preI1A2UntrackedLoss`가 4라고 해서 새 패치 자연주행에서 처음부터 오류 4개가 발생했다는 뜻은 아니다. 이는 이전 엔진 실행 중 발생한 설명 불가 결손의 보존적 이월 수량이다.

## 4. 장비 보존식 및 물리성

품목별 불변식:

```text
누적 생산 + legacy 마이그레이션
  = 국가 지역 재고
  + Person 장착 장비
  + Formation 회수품 cache
  + 공식 전장 유실
  + legacy 미추적 손실 (pre-I1A2 이월 포함)
```

비전투 사망, 국제 이주, 국가 귀속 변경은 **기존 장착 장비 → 원 국가 지역 재고**로 같은 품목의 수량을 이동시킨다. 누적 생산이나 전장 유실을 조정하지 않으며 Gold, Person, 식량, 목재, 철, 도구를 생성하지 않는다. 기존 지역 저장 용량을 초과한 강제 회수 시 기존 I1의 `storageOverflows` 진단을 유지한다.

I1A1 전장 회수 로직은 다음과 같이 불변이다.

| 상황 | 성공 확률 |
|---|---:|
| 진행 중 라운드 승리측 | 85% |
| 진행 중 라운드 패배측 | 55% |
| 진행 중 승패 불명 | 65% |
| Engagement 종료 패배측 일반 후퇴 | 35% |
| Engagement 종료 패배측 깊은 회복 | 20% |

- 무기/방어구 슬롯은 독립적으로 확률 판정한다.
- 회수된 현장 장비는 Formation 회수품 cache에 있다가 해당 Formation이 유효 공급 노드로 돌아올 때 재고화한다.
- 공식 회수 실패·전멸 유실은 `battleLostByItem`에 반영한다.
- 일반 부상자는 장비를 계속 보유한다.

2. 로컬 PC의 `village-observer-v034A-save-...json`을 선택하고 **구조 검사 시작**을 누른다. 파일은 브라우저의 독립 Worker에서 읽고 JSON 파싱 및 검사한다.
3. **경량 JSON 보고서 다운로드**를 눌러 결과를 저장한다. 원본 세이브는 수정·재저장·외부 전송하지 않는다.
4. 대규모 성장 세계 검증은 보고서만 공유할 수 있다. 0.34B 변환 시 동일 날짜의 변환 전후 보고서 두 개를 비교한다.

**검사 범위**: `map.tiles[]`, `villages[]`, `residents[]`, 영토/ownerId 양방향 일치, Nation/Tile/Person ID 중복, 거주·근무 타일의 존재, 음수·비유한 타일 재고, 타일별 폐허 실물 장비와 Nation 폐허 잔존 원장 합계. 엔티티 상태의 SHA-256 128비트 지문과 JSON 최상위 영역별 저장 바이트 수도 출력한다. 지문은 비교 편의를 위해 34B의 신규 `settlementId`/`v34b` 필드를 제외한다.

**불포함**: `World.from()`으로 재불러오기 및 저장 왕복, 날짜 진행, 기존 정식 I1 장비 전량 보존식 감사, 세계 전체 Gold 유량 감사, 모든 물류 경로의 정상성 및 0.34B Settlement 스키마 검증. 0건 오류는 **정적 구조 검사 통과**만 의미한다. 대용량 JSON 파싱에 충분한 브라우저 메모리가 필요하며 실제 사용자 96.80MB 세이브에 대한 검증 결과는 사용자 로컬 검사 전까지 알 수 없다.

세부 사용법·검증 범위: `LOCAL-SAVE-VALIDATOR.md`, 통제 검증 결과: `TEST-LOCAL-SAVE-VALIDATOR.md`.
