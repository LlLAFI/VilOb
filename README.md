# Village Observer V0.21

Village Observer는 실제 주민(Person)의 생활과 선택이 Settlement → Nation → World의 변화로 이어지는 **bottom-up 자율 사회 시뮬레이션**입니다.

이번 V0.21 보강판은 100×100 한반도 장기주행에서 확인된 두 문제를 집중적으로 수정합니다.

1. 인구가 크게 늘어도 개척 가능한 정착지가 거의 생기지 않아 영토 확장이 정체되는 문제
2. 30년 이후 배속 주행 렉과 AUTO_5_DAY 전체 snapshot 누적으로 devlog가 급격히 커지는 문제

장거리 접촉·교역, 철/제련, 360일제는 이번 보강판에 포함하지 않습니다.

---

## 1. 확장 밸런스 보강

### 지역 단위 개척민 풀

기존 V0.21은 한 정착지 안에서 개척민 2~3명과 잔류 성인을 모두 확보해야 했습니다. 70년 테스트에서도 성숙 정착지는 많지만 `eligibleFrontierSettlements`가 거의 0인 상태가 반복되었습니다.

보강판에서는 **출발 정착지와 반경 2 이내의 연결된 아군 정착지들이 실제 잉여 성인을 모아 개척대를 구성**할 수 있습니다.

- 실제 Person만 Pioneer가 될 수 있음
- 각 donor 정착지에는 최소 성인을 남김
- 이미 Pioneer인 주민은 중복 동원 불가
- 출발 정착지 자체는 기존처럼 성숙 상태여야 함
- 국가 전체의 추상 인구 숫자를 직접 개척민으로 변환하지 않음

따라서 `인구 증가 → 지역별 성인 잉여 → 복수 프런티어`라는 구조를 유지하면서 한 타일의 우연한 연령분포 때문에 개척이 장기간 봉쇄되는 현상을 완화합니다.

### 성향별 위험 허용도

물리 규칙은 같지만 개척에 필요한 잔류 성인·비축·밀도 기준은 성향에 따라 다르게 평가됩니다.

- **영토확장형**: 가장 낮은 잔류 기준과 밀도에서도 개척 허용
- **자원개척형**: 영토확장형 다음으로 적극적이며 자원가치 방향을 선호
- **균형형 / 교역외교형**: 중간 수준의 안전성 요구
- **생존안정형**: 더 많은 잔류 성인과 비축 요구
- **도시집약형**: 가장 높은 밀도를 요구하고 조밀한 확장을 선호

Flat 생산 보너스가 아니라 동일한 상황을 해석하는 기준만 다르게 유지합니다.

### 2명 기본, 3명 개척대는 제한적으로

기본 개척대는 실제 Pioneer **2명**입니다.

3명 규모 개척대는 다음처럼 충분한 인구 여력이 있을 때만 구성됩니다.

- 출발 정착지 인구가 충분함
- 지역 Pioneer pool에 최소 4명의 잉여 성인이 존재
- 국가 인구밀도도 충분히 높음

V0.21 초기판에서 3인 개척대와 잦은 후속 보강이 인구를 지나치게 분산시키던 문제를 줄였습니다.

### 변경 보강은 위기 거점에만

`FRONTIER_REINFORCEMENT`는 더 이상 인구 2~3명의 정상 변경을 계속 채우지 않습니다.

현재 자동 보강은 기본적으로:

- 변경 주민이 **1명까지 감소**
- 충분한 국가 식량/인구밀도
- donor 정착지 인구·성인·식량 여유
- 해당 변경의 최근 보강 cooldown 경과
- 이동할 Person의 마지막 이주 후 **360일 이상** 경과

조건을 만족할 때만 실제 주민 1명을 이동시킵니다.

목표는 `개척 → 반복 보강 → 다른 정착지 성인 부족 → 개척 차단` 루프를 끊는 것입니다.

## 2. 런타임 성능 최적화

### 중복 정착지 유지 검사 제거

기존 코드에서는 정착지 유지 검사가 Village daily tick 내부와 World daily 진행부에서 중복 실행되고 있었습니다.

보강판에서는 하루에 한 번만 실행합니다.

### 정착지 유지 로직 1-pass화

기존 `maintainSettlements()`는 빈 정착지를 검사할 때 donor 후보마다 전체 주민 배열을 여러 차례 다시 검색했습니다.

보강판은 하루의 주민별 거주 타일 수를 한 번 집계하고 그 결과로 donor를 고릅니다.

영토와 인구가 커질수록 발생하던 불필요한 반복 검색을 줄입니다.

### 일일 구조값 캐시

Person들이 하루 행동을 수행하는 동안 다음 값은 구조적으로 거의 변하지 않습니다.

- 국가의 살아 있는 인구 수
- 활성 주거 capacity
- 저장 capacity

기존에는 각 Person의 직업 선택·대사·행동에서 이 값들을 반복 계산했습니다. 보강판은 **한 국가의 daily tick 동안 한 번 계산한 값을 재사용**하고 하루가 끝나면 캐시를 해제합니다.

건물 완성, 출생, 연간 처리 등 다음 구조 변경 시점에는 정상 계산으로 돌아갑니다.

### V0.21 개척 계산 주민 인덱스

프런티어 판단에서는 `tileResidents()` 전체 검색을 반복하는 대신 해당 simulation day의 **거주 타일 → 실제 Person 배열 인덱스**를 재사용합니다. 개척 완료나 보강 이주처럼 거주지가 바뀌면 캐시를 무효화합니다.

## 3. Devlog / snapshot 최적화

V0.20~초기 V0.21 장기 로그 분석에서 devlog 용량의 주원인은 이벤트 문자열보다 **AUTO_5_DAY 전체 상태 snapshot**이었습니다.

보강판은 자동 snapshot 생성 주기를 시뮬레이션 연령에 따라 조절합니다.

| 시뮬레이션 시기 | 자동 snapshot |
|---|---|
| 1~10년 | 5일마다 |
| 11~30년 | 15일마다 |
| 31년 이후 | 30일마다 |

그리고 세계가 오래될수록 메모리에 남은 과거 snapshot을 계층형으로 압축합니다.

- 최근 약 10년: 현재 해상도 유지
- 약 10~30년 전: 30일 간격만 유지
- 그보다 오래된 자동 snapshot: 120일(1년) 간격만 유지
- `WORLD_START`, `MANUAL` 등 비자동 snapshot은 보존

이 방식은 최근 변화 분석 능력을 유지하면서 오래된 세계의 중복 상태 사본을 크게 줄입니다.

이벤트 로그 자체의 역사적 사건은 이번 패치에서 대규모 삭제하지 않습니다. snapshot이 실제 용량의 주원인이었기 때문에 먼저 그 부분을 최적화합니다.

Devlog JSON의 `worldSummary`에는 다음 정책 설명도 기록됩니다.

- `frontierBalance`
- `performance`
- `devlogPolicy`
- `snapshotCount`

## 5. 개발 회귀 테스트

### 100×100 자연맵 deterministic 20년 비교

동일한 난수 시드의 개발용 100×100 자연맵에서 초기 V0.21과 보강판을 비교했습니다. 지형은 한반도 MapData가 아닌 개발용 자연맵이므로 절대 밸런스 수치가 아니라 **회귀/성능 확인용**입니다.

대표 실행에서 보강판은 비슷한 인구 규모에서:

- 영토: 약 46 → **49타일**
- 개척 시작: 약 46 → **53회**
- 변경 보강: 약 137 → **61회**
- 폐허: 4 → **5회**

수준으로 나타났습니다. 즉 반복 보강을 크게 줄이면서도 개척은 감소시키지 않는 방향을 확인했습니다.

### 실행시간

같은 개발 환경에서 100×100 20년 주행은 대표 실행 기준 약:

- 초기 V0.21: **17.7초**
- 보강 V0.21: **13.8초**

수준이었습니다. 실행환경과 난수 결과에 따라 달라지므로 절대 성능 보장은 아니며 회귀 비교값입니다.

### Devlog 크기

동일한 20년 개발 조건의 JSON 직렬화 크기는 대표 실행에서:

- 초기 V0.21: 약 **18.9 MB / 481 snapshots**
- 보강 V0.21: 약 **5.8 MB / 121 snapshots**

로 감소했습니다. 보강판 쪽 이벤트 수가 더 많았음에도 snapshot 축소 효과가 더 컸습니다.

### 30년 스모크 테스트

보강판 100×100 개발용 자연맵을 30년 진행하여:

- 구문 오류 없음
- 6/기본 국가 시뮬레이션 정상 진행
- 개척/영토 획득 지속
- snapshot 계층화 정상 작동
- 저장/불러오기 후 진행 정상

을 확인했습니다.
